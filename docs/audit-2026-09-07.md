# Pre-launch audit — 2026-09-07

Read-only audit of the live production stack across five dimensions, run in parallel;
every finding then passed to an adversarial reviewer instructed to refute it and to
re-probe production itself. 11 agents, 0 errors, 755 tool calls, ~51 min.

**29 findings** (21 confirmed, 2 refuted, 1 uncertain, 5 no verdict returned) plus **15 coverage gaps** the five dimensions never looked at.

Severities below are POST-REVIEW. `NO-VERDICT` means the reviewer returned a verdict
under a reworded title and it could not be matched automatically — treat those as
unreviewed, not as dismissed.

## Already fixed

Two findings were fixed and verified against production before this report was written.
They are still listed in full below, with a STATUS line, because the evidence explains a
whole class of bug rather than one instance.

- **`can_view_book` parameter shadowing** — migration `20260907170000`. An unqualified
  `book_id` in a `LANGUAGE sql` body resolved to the COLUMN, not the parameter, so the
  function ignored its argument and three RLS policies (books, audiobook_assets,
  comments) collapsed permissive on the first publish. Proven live with the fix in
  place: publishing one version made exactly 1 book anon-visible instead of all 23.
- **`readings.id` had no DEFAULT** — migration `20260907170100`. Every reading-progress
  insert failed 23502 and the error was discarded; nothing had been saved since
  2026-04-02.

## Two patterns worth reading the whole report for

**A green check is not evidence.** The Stripe blocker below is green in the repo's own
`check:launch-config` gate, because that gate asserts only that the variable is
*present*. And `launch-config.test.ts:192` puts `sk_test_x` into `goodEnv()` and asserts
zero errors — the test suite pins the blind spot open. The same shape appeared twice more
the same day: the admin-unpublish test asserted the broken transition, and CI had failed
on every run in the repo's history so a red check had stopped meaning anything.

**Migrations recorded but never run.** `20260317120000_pod_orders` is the third instance
found: the ledger says applied, none of the DDL exists, and `db push` is therefore a
no-op that cannot self-heal. Every migration should be diffed against the live schema,
not against the ledger.

#### First publish flips books, audiobook_assets and comments to fully world-readable, because can_view_book's shadowed parameter makes it a global "is anything published?" flag

- **verdict** `NO-VERDICT` · **dimension** `rls-exposure` · **evidence quality** `verified-live`
- **STATUS: FIXED 2026-09-07 — migration 20260907170000. Proven live: one published version now exposes 1 book, not 23.**
- **where** apps/web/supabase/migrations/20260204093000_fix_books_visibility_rls.sql:20 (WHERE bv.book_id = book_id); policies at 20260204093000_fix_books_visibility_rls.sql:33 (books), 20260207090000_worker_contract_and_storage.sql (audiobook_assets_select), 20260210110003_community_comments_and_follows.sql (comments_select_visible_books)
- **evidence** Live: GET /rest/v1/rpc/can_view_book?book_id=00000000-…&viewer_id=00000000-… with the anon key returned HTTP 200 and body `false` — so an unauthenticated internet caller holds EXECUTE on this function and can query it for any book id. The function is LANGUAGE sql SECURITY DEFINER with `SET row_security = off`, and its predicate is `WHERE bv.book_id = book_id` where `book_id` is both the parameter name and a column of the `book_versions` alias `bv`. PostgreSQL resolves an unqualified name in a SQL-function body to the column, not the parameter, so this compiles to `bv.book_id = bv.book_id` — always true. `viewer_id` does NOT shadow (no such column on book_versions/books/author_followers), so only the book-identity half of the predicate is destroyed. The function therefore reduces to `EXISTS (SELECT 1 FROM book_versions WHERE published_at IS NOT NULL AND visibility='public')` — a global boolean, ignoring its book_id argument entirely. Grep confirms exactly three SELECT policies call it: books (`author_id = auth.uid() OR can_view_book(id, auth.uid())`), audiobook_assets, and comments. It currently returns `false` only because zero book_versions are published, which is precisely today's masking condition.
- **fails like this** An author publishes the first book on launch day, setting one book_versions row to published_at NOT NULL / visibility='public'. can_view_book now returns true for every uuid, for every caller including anon. All three policies collapse to permissive. Anyone runs `curl -H "apikey: <NEXT_PUBLIC_SUPABASE_ANON_KEY>" "https://<project>.supabase.co/rest/v1/books?select=*"` and receives every row in the books table — every unpublished DRAFT manuscript title/description, every followers-only and private book, for every author on the platform — plus every audiobook_assets row (audio_path storage keys and generation metadata for unreleased audiobooks) and every comments row. The Next.js app is bypassed entirely; its own access checks never run.
- **fix** Rename the parameters so they cannot be captured by a column in scope, e.g. `can_view_book(p_book_id uuid, p_viewer_id uuid)` with the predicate `WHERE bv.book_id = p_book_id`, or qualify via `$1`. Because the live schema is not reliably described by the migrations, verify with `SELECT prosrc FROM pg_proc WHERE proname='can_view_book'` before and after. Then add a regression test that publishes one book and asserts can_view_book(<other book id>, NULL) is false. Audit the same shadowing pattern anywhere else a SQL function parameter shares a name with a column of a table in its own FROM clause.
