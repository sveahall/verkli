## Original schema-free design assessment

The existing contract can hold a distinct completion marker without a migration:

- `20260210020000_subscription_billing.sql:27–32` creates text `stripe_event_id` with UNIQUE and text `type`, plus timestamp `received_at` defaulting to now.
- `20260210030000_subscription_billing_schema_alignment.sql:48–76` makes the event ID the primary key and removes `payload`; do not write a payload or invent a processed-status column.
- Generated `apps/web/src/lib/supabase/types.ts:3439–3455` agrees: only `stripe_event_id`, `type`, `received_at`.
- `20260327110000_security_hardening_beta_round2.sql:6–18` states service-role-only access. No event-ID-format constraint, type enum, or foreign key was found in the repo.
- Production-code search found only the generic record/rollback helpers using this table. They address exact IDs; no consumer was found that enumerates every row and sends the stored ID to Stripe. Live schema was not queried.

The following recommendation was implemented by another agent and checked above:

1. Reserve a separate marker such as `stripe_event_id = "book-download-email:" + sessionId`, `type = "book_download_email.accepted"`. Document that this is an application acceptance receipt, not a real Stripe event and not proof of inbox delivery.
2. Before sending, read that exact marker using the existing admin client. Existing marker means the email was accepted and the send is skipped, including new event IDs for the same session and retries beyond Resend's supplied 24-hour idempotency window. A read error must propagate rather than being treated as absence.
3. Send using the existing stable provider idempotency key. After a successful provider acceptance response, insert the marker. Accept a unique conflict as another successful writer's completion; propagate other marker-write errors so retry remains possible. Never insert the completion marker before the send.
4. In the **duplicate** webhook path, run only this recovery helper, and only after successful signature verification for `checkout.session.completed` or `checkout.session.async_payment_succeeded`, `payment_status === "paid"`, `payment_kind === "book_order"`, and `order_variant === "ebook"`. Do not replay the generic payment handler for all duplicate events. Keep the same eligibility check shared with the ordinary path.
5. Generic failure rollback must delete only the real `evt_...` claim; it must not delete the namespaced completion marker. Check failures and send failures must return a retryable server error. Keep logging under the existing feature prefixes and avoid logging the personal download URL.

**Remaining uncertainty to state explicitly:** provider acceptance and the DB marker cannot be atomic. If the provider accepted but the process exited or marker write failed, the stable provider key suppresses duplicates only within its own retention window. An automatic resend after that window can duplicate an email. The marker solves indefinite duplicate suppression *once recorded* and recovery from failed sends; it does not provide exactly-once delivery across an unrecorded provider acceptance. Reconciliation or manual handling is needed for that uncertain old-attempt window. The 24-hour window is the integrator-supplied provider contract, not independently browsed in this read-only task.

The requested hermetic regressions, now present in the final test file, were:

- Existing generic claim with no completion marker still retries and completes the paid e-book email; include failed rollback and process-exit seed variants.
- Existing completion marker skips the provider for both the same event and a distinct paid event for the same session; simulate a time beyond the provider window.
- Marker read failure performs no send and returns 500. Marker write failure after acceptance returns 500; replay uses the same provider key and eventually records completion.
- Concurrent callbacks use the same provider key, and a duplicate marker insert is successful completion rather than an error.
- Unsigned/invalid-HMAC requests still do no DB/email work. Duplicate unpaid, print, unrelated-payment and unrelated-event callbacks still do no e-book delivery.
