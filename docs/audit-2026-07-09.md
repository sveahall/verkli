## 1. Where we are

The platform is **built and in GA-readiness / hardening**, not in planning. This
is polish-and-harden territory, not rescue. Concretely:

- **341 route directories**, deep feature set: author dashboard + editor (Tiptap),
  reader app, discover, library, clubs, polls, newsletters, messaging, marketing
  campaigns, print-on-demand, referrals, analytics, admin panel.
- **93 DB migrations** through 2026-07-05 (per-chapter pricing, Stripe Connect
  payouts, POD, audit_log, content reports, account-deletion, search FTS, voice
  cloning, author subscriptions, investor demo façade, 3 security-hardening rounds).
- **AI layer** (`src/lib/ai`): translation (Opus MT + NVIDIA Riva, chained),
  content-generation (cover images via NVIDIA SD3, image→video via Higgsfield),
  trailer-generation, writing-assistant (NVIDIA NIM / Llama). TTS is **ElevenLabs**
  (sole backend — the "Qwen TTS" in old docs was wrong and is now fixed).
- **Workers** (BullMQ): import, translation, audiobook, marketing, social-publish,
  notifications, recommendations, combined. Guardrail kit exists (budget caps,
  circuit-breaker, idempotency, timeout).
- **Security posture is strong**: HMAC-verified Stripe webhooks with idempotency,
  OAuth with HMAC state + PKCE + AES-256-GCM token encryption, layered CSRF in
  middleware, DB-`profiles.role`-only authorization, server-side newsletter
  sanitization, timing-safe admin auth. No hardcoded secrets found.

## 2. What we fixed this pass

All verified against the code and passing lint + `tsc` + the full test suite;
codex gave the diff a PASS (no P1).

1. **Reading progress could regress (HIGH).** Re-opening an earlier chapter of a
   finished book overwrote the `readings` row backward (100% → 20%), which broke
   "Continue reading" and demoted the book out of the Finished shelf.
   `ReadingProgress.tsx` now gates on the integer `current_chapter` (rounding-safe)
   and only advances; re-reading an earlier chapter bumps `last_read_at` only.
   Skips the write on a read error rather than risk regressing.
2. **Social-publish marked "completed" when every platform failed (HIGH).** The
   author's UI reported a successful publish while nothing was posted. The worker
   now marks the job `failed` with the failed-platform list when any publishable
   platform fails.
3. **Dead code removed.** 4 never-imported feature-flag accessors
   (`getAiChatEnabled`, `getDonationsEnabled`, `getDemoFacadeEnabled`,
   `isRecommendationsEnabled`) deleted from `flags.ts` (live siblings remain).
4. **Docs corrected** (see §5).

## 6. AI-engine readiness (toward the "plug in many AI agents" vision)

The vision is a heavily componentized platform where an AI engine with many agents
plugs in cleanly. **Today there is exactly one clean seam: translation.** A
`TranslatorProvider` interface + registry (`getTranslatorForPair()`) lets you add
backends without touching callers. Everywhere else, "AI" is point integrations
hardwired to concrete vendors. Gaps to close, in priority order:

1. **Provider interfaces for text/image/video** mirroring `TranslatorProvider`, with
   a registry resolved by capability — so `generate.ts` depends on interfaces, not on
   `higgsfield`/`nvidia-sd3` modules directly (`generate.ts:131`).
2. **One job contract.** Content-generation runs synchronously inside the HTTP request
   (`content_assets`, up to 5-min blocking); video/trailer/marketing use `ai_jobs` +
   BullMQ. Two state machines, two status vocabularies. Unify on one `GenerationJob`.
3. **Central `ai_jobs.kind` registry.** Allowed kinds are re-declared in ≥3 places with
   divergent spelling (`text_to_video` vs `text-to-video`). One source of truth mapping
   kind → queue → worker → status.
4. **Shared NIM/OpenAI-compatible chat client.** The endpoint/model/auth is copy-pasted
   across `writing-assistant.ts` and `nvidia-riva-translator.ts`.
5. **Agent/Capability abstraction.** No `Agent`/`Tool`/capability interface exists — the
   seam the vision needs. Use the translation registry as the template.
6. **Apply the worker guardrail kit** (budget/circuit-breaker) to the synchronous AI
   paths, which currently reinvent ad-hoc in-memory rate limiting per route.

Two "AI" paths are currently **stubs shaped to look pluggable**: content-generation's
`generateText` builds LLM prompts then returns hardcoded Swedish templates; trailer
generation only ever returns genre templates. Decide: wire a real provider, or make
them honestly template-only.
